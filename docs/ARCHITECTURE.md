# Architecture

## Layers

```text
gui/ (DearPyGui)              displays, dispatches, never computes an explanation
  │  calls
api.py ── core/pipeline.py    runs over a project's events, writes run folders
  │
  ├── methods/                occlusion (numpy), Grad-CAM (torch), baselines
  ├── analysis/               scoring in both identity modes, re-detection matching, summaries
  ├── io/                     frames, project, run folders, schema, YORU CSV import
  ├── visualization/          colour tables, overlays, preview PNGs
  └── adapters/               the only code that runs a model
        ├── base.py           the ModelAdapter contract
        ├── yolov5.py         YORU's YOLOv5, reproduced step by step
        ├── _yoru.py          the only module importing YORU internals
        └── toy.py            synthetic detector with known answers (tests, demos)
core/                         types, errors, geometry, hashing, logs, registry, environment
```

Rules, checked by `tests/unit/test_yoru_boundary.py`:

* `core`, `analysis`, `io`, `visualization` and `methods/occlusion.py` import
  neither torch nor a GUI toolkit nor YORU at module level; the core runs
  headless. DearPyGui and tkinter (file dialogs) are imported in `gui/` only.
* YORU names outside YORU's documented external API appear only in
  `adapters/_yoru.py`.
* YORU never imports `yoru_explain`; YORU's GUI has no branch for it.
* No `argparse`: settings are dataclasses / dicts / JSON; the GUI starts with
  `python -m yoru_explain`, and `app.main()` takes its options as arguments.

## The adapter contract (`adapters/base.py`)

| Method | Contract |
|---|---|
| `load_model(weights, device, **options)` | load; measure capabilities (determinism, batch dependence, gradient probe) |
| `preprocess(images)` | frames of one shape → batch tensor + `LetterboxTransform` |
| `predict_raw(prepared, logits=)` | one forward pass exactly as the detector's own inference (no grad, same autocast) → `RawOutput.pred (B, N, 5+nc)` |
| `postprocess(raw, prepared)` | the detections the detector reports, each with its `CandidateRef` |
| `candidate_readout(raw, prepared, k, c, score_type)` | candidate `k`'s score, box, class on every image |
| `score_target(raw, prepared, target, score)` | `ScoreResult` per image in fixed-candidate or re-detection mode (`analysis/scoring.py`) |
| `identity_check(image)` | compare with the detector it stands in for |
| `gradient_layers()`, `default_gradient_layer()`, `forward_with_gradients()`, `candidate_score_tensor()` | the gradient path |
| `capabilities` | `fixed_candidate`, `redetection`, `score_types`, `gradients` + reason, `gradient_layers`, `deterministic`, `batch_invariant`, `batch_max_abs_diff` |

An adapter never calls `.train()`, never makes parameters require gradients
and never writes weights; one `RLock` per adapter serialises forward passes
between the GUI's threads.

### The YOLOv5 adapter

It builds the model with YORU's own `load_yolov5_model` and repeats
`YOLOv5Detector.detect` step by step — YORU's channel-order rule, AutoShape's
preprocessing with the bundled `letterbox`/`make_divisible`, the forward pass
under `inference_mode` + `autocast("cuda")`, the bundled
`non_max_suppression` at `min(conf, 0.25)`, the conf threshold after NMS,
`scale_boxes`. NMS is called once per image even for a batch, as YORU calls
it: the bundled NMS has a per-call time limit after which it returns the
rest of a batch empty. Because it calls the bundled functions rather than copies of
them, the detections are YORU's by construction; `identity_check` confirms it
on every run.

The pre-NMS candidate of each detection is recovered from NMS's output: NMS
keeps candidate rows unchanged, so the output box equals `xywh2xyxy(pred[k])`
of exactly one `k`, bit for bit. (Re-implementing NMS with an index column was
the alternative; YOLOv5's NMS multiplies extra columns by objectness and
would have needed a second NMS implementation that could drift from YORU's.)

Gradients: the checkpoint's parameters do not require gradients (EMA
weights), so the graph starts at a copy of the input with `requires_grad`;
the Detect head's anchor-grid cache, created under inference mode, is swapped
for ordinary clones during the gradient pass and restored after.

## A run (`core/pipeline.run_analysis`)

```text
config.json  ← the request (written first)
manifest.json (status: running)
for each event, by source and frame:
    frame  ← decoded in order (exact numbering); hash == event's hash?   else frame_mismatch
    first frame: adapter.identity_check(frame)                          failed → stop the run
    target ← reproduce_target: same candidate+class with IoU ≥ 0.9, or class + IoU ≥ 0.9
             (event made with another model: IoU only)                else target_not_reproduced
    cache key = sha256(model, adapter settings, device, frame hash, target, method config)
    hit → copy the earlier result (cached_from)
    else → occlusion / Grad-CAM → maps/*.npz, previews/*.png, then perturbations.csv rows,
           then the results.csv row last; a write error removes the event's files -> output_failed
manifest.json (status, identity check, counts, error codes)
```

Rows are appended per event, so an interrupted run keeps valid tables of
what it finished.

## Occlusion and batches

Perturbed frames are scored in batches of `batch_size`. Every batch is padded
to the same size, and the reference score is measured in a batch of that size,
because the detector's numbers depend on it (`docs/VALIDATION.md` §2). The
unchanged frame runs through the same pipeline as a control (`noop`), which
also checks this logic on every target. A CUDA out-of-memory error fails the
target with `cuda_oom`; the batch size is never changed silently mid-run.

## Frames

`io/frames.VideoFrameReader` numbers frames as YORU's analysis does (in
decoding order from 0) and returns each frame with its presentation time, a
pixel hash and how it was reached. Far jumps use a seek verified against a
presentation-time index built by one in-order pass; unverifiable seeks fall
back to in-order reading. Analysis runs always read in order.

## Threads (GUI)

* The render loop (`gui/main_window.run`) runs DearPyGui's callbacks itself
  (manual callback management), so every callback is on the render thread; a
  callback that raises is shown in a popup and logged, and the loop goes on.
  The window shell is YORU's `GuiSession` (screen-fitted viewport, Japanese
  font, Window menu, remembered size) with YORU's theme and a pink accent.
* `TaskRunner` — one long task at a time (load a model, an analysis run, a
  seek check) on its own thread; cancellation is a `threading.Event` the
  pipeline polls between batches and events.
* `FrameService` — decodes frames and runs the detector for the Explore view
  on a second thread, keeping only the latest request (slider dragging).
* Neither touches DearPyGui. They leave progress and results behind; the
  loop calls `poll()` once per frame and delivers them as `state.Signal`
  callbacks on the render thread.
* Closing the window during a task asks first, cancels, and keeps rendering
  until the task reaches its next check (at most 60 s), so its run folder is
  closed with a manifest.
* Explore's frame is an ImPlot image series whose axes are frame pixels
  (y downwards; the texture's UVs are flipped for that); textures above
  2048×1536 are downscaled for display only.

## Logs

`~/.yoru/logs/yoru_explain.log` (YORU's log directory, via the documented
`get_log_dir`), rotating 5 MB × 3; each run also writes `logs/run.log`. Tests
point `YORU_HOME` at a temporary directory.
